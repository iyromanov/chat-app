# Стандарты реализации и ревью

Поведение и технические решения определены в [.scratch/chat-app/spec.md](.scratch/chat-app/spec.md). Обоснования существенных компромиссов находятся в [docs/adr](docs/adr).

## Язык кода и приложения

- Русский язык допускается только в Markdown-файлах (`.md`). Все остальные файлы проекта, включая тесты и тестовые данные, писать на английском; для проверок Unicode использовать символы без русского текста.
- Все комментарии в коде, включая JSDoc/TSDoc, весь текст UI приложения и все сообщения об ошибках писать на английском. Это включает ошибки валидации, HTTP API, Socket.io и внутренние ошибки приложения; правило распространяется на существующий и новый код.
- Пользовательский контент (сообщения, username и другие введённые данные) сохранять на языке пользователя. Документация проекта может оставаться на русском.

## Асинхронные вызовы

- Вызовы без ожидания записывать напрямую: `load()`, а не `void load()`. Оператор `void` не использовать; тип `void` в сигнатурах сохранять.
- Если завершение операции нужно текущему потоку, использовать `await`. Ошибки фоновых операций обрабатывать внутри вызываемой функции или через `.catch(...)`; удаление `void` не заменяет обработку ошибок.

## Организация классов

- Члены класса располагать в следующем порядке:
  1. Приватные поля и свойства.
  2. Публичные поля и свойства.
  3. Конструктор.
  4. Публичные методы.
  5. Приватные методы.

## Frontend

- Соблюдать направление импортов FSD: app → pages → widgets → features → entities → shared. Один срез обращается к другому через его публичный интерфейс, а не к внутренним файлам; соседние entity-срезы не связывать ради обновления stores.
- App и Shared не делятся на предметные срезы; их внутренние сегменты могут взаимодействовать. Слои и срезы добавлять при необходимости.
- Предметные действия и состояния размещать по ответственности, указанной в спецификации. Готовые UI-компоненты импортировать из `flowbite-svelte`; оформление настраивать через поддерживаемые библиотекой параметры, классы и тему. Допускается настройка цветов, размеров, скруглений и визуальных состояний. Tailwind-классы использовать для раскладки и этих настроек оформления согласно ADR 0006. Предметные композиции размещать в соответствующих слоях FSD.
- Stores и транспорт создавать для экземпляра приложения. Общие серверные переменные не содержат пользовательское состояние. Выход очищает данные текущего пользователя.
- Shared не импортирует app; потерю авторизации передавать наверх через интерфейс клиента. Управление соединением и связывание событий с предметными stores выполнять в app.

## Backend и контракты

- Для пагинации списков в API использовать `paginate` из [apps/api/src/common/pagination.ts](apps/api/src/common/pagination.ts). Загрузку данных и определение позиции элемента передавать в общий helper; размер страницы, обработку курсора и формирование `nextCursor` централизовать в нём.
- Контроллеры и gateway делегируют прикладным сервисам. Проверки участия и срока доступа принадлежат прикладной логике; guards и pipes выполняют транспортные проверки.
- Моделями MongoDB владеет соответствующий NestJS-модуль; другие модули используют экспортируемые сервисы.
- Mongoose-схемы отделять от Zod-контрактов. Пакет контрактов не зависит от NestJS, Mongoose или Svelte.
- Публичные ответы не содержат Mongoose-документы, хеши, внутренние ошибки БД или stack trace.
- HTTP-вызовы frontend выполнять через согласованный клиент. Сгенерированные типы обновлять генератором вместе с OpenAPI; вручную их не редактировать.
- При повторных запросах и событиях соблюдать правила идемпотентности и объединения данных из спецификации. Уникальность защищать индексами, а не только предварительным чтением.
- Дополнительные слои и абстракции вводить для конкретной необходимости текущего объёма.

## Проверка изменений

- Тестировать внешнее поведение через согласованные HTTP/Socket.io-интерфейсы; требования и независимые примеры служат источником ожидаемых результатов.
- Использовать MongoDB в Testcontainers для проверок сохранения, уникальности и конкурентных операций; истечение сроков проверять с управляемым временем.
- Автоматические правила форматирования, типов, импортов и актуальности генерации проверять инструментами. Ревью сосредоточить на поведении, ответственности модулей и правилах, которые инструменты не покрывают.
