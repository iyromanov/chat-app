# Журнал обсуждения архитектуры состояния UI

Журнал обсуждения; итоговая архитектура — в [spec.md](spec.md). Реализация не начата и не разрешена текущим запросом.

## Контекст

Пользователя не устраивает текущая организация состояния UI. Исходное предложение — RootStore + Controllers + Domain Stores на Svelte 5 runes. Его необходимо проверить на текущем коде и уточнить до реализации.

Уточнение цели: упрощать также бизнес-логику до разумного объёма тестового задания с чатом. Сохранение всех ранее добавленных гарантий не является обязательным. Пользователь явно поручил отказаться от `attemptId`. Новые имена модулей без сокращения ненужной сложности не решают задачу.

Приоритеты исходного предложения: читаемость, предсказуемый поток данных, разделение ответственности, поддержка и тестирование, минимум boilerplate, FSD. Каждый бизнес-сценарий должен иметь понятную точку входа; изменения состояния должны прослеживаться по явным вызовам.

Базовое поведение приложения описано в [спецификации чата](../chat-app/spec.md), ограничения реализации — в [CODING_STANDARDS.md](../../CODING_STANDARDS.md). Новые решения не считаются заменой действующих ADR до явного согласования.

Принятое здесь удаление `attemptId` заменяет прежнее требование идемпотентной отправки в спецификации чата и задаче 05. Старые документы описывают реализованное поведение до этой миграции. Изменения контракта отправки входят в обсуждаемую цель; прежнее ограничение исходного предложения «не менять backend API» не блокирует это явное указание пользователя. Код, контракты и существующие тесты пока не изменяются.

Подтверждённое упрощение восстановления заменяет прежнюю гарантию автоматического получения всех пропущенных страниц: после reconnect/возвращения на вкладку загружаются последние 50 сообщений, старая пагинация сбрасывается. См. [ADR 0008](../../docs/adr/0008-simple-message-delivery.md).

## Проверенные исходные факты

- `apps/web/src/app/runtime/runtime.svelte.ts` уже создаёт и связывает auth, chat и realtime. Для каждого успешного входа создаётся новый авторизованный контекст.
- [ADR 0007](../../docs/adr/0007-authenticated-client-context.md) закрепляет пересоздание HTTP-клиента, stores сообщений и диалогов и Socket.io при новом успешном входе. Обычная перепроверка авторизации и reconnect сохраняют контекст.
- `apps/web/src/app/chat/chat.ts` уже координирует подтверждение отправки, обновление истории и превью через `messageSaved`.
- [ADR 0004](../../docs/adr/0004-message-source-of-truth.md) требует объединять REST и события, восстанавливать данные при reconnect и возвращении на вкладку.
- Auth, Messages и Conversations уже реализованы через runes. Два эффекта UI обслуживают DOM, а не синхронизацию доменных stores.
- HTTP, пагинация и восстановление находятся внутри Messages/Conversations; HTTP login/register/start conversation — в компонентах; send/retry — в reactive composer model.
- Сейчас Messages хранит историю одного открытого диалога и очищает её при переключении. Коллекция историй по `conversationId` вводит новый кэш и требует отдельной политики.
- Попытка отправки содержит неизменяемые `attemptId` и текст; её может подтвердить HTTP, WS или REST-история. Редактирование черновика не меняет повторяемую попытку.
- Recovery использует обычную пагинацию newest → older до ранее загруженной границы. Параметр `after` был удалён по согласованию в [задаче 05](../chat-app/issues/05-recover-connection-and-retry-send.md); ранние упоминания в исходной спецификации устарели.
- События включают `auth:ready`, `auth:ended`, `message:created`, `conversation:created`. Unread count и реализованные story-модули отсутствуют.
- Текущий HTTP-клиент основан на `swagger-typescript-api` согласно [ADR 0005](../../docs/adr/0005-zod-openapi-client.md); ранние записи об openapi-fetch устарели.
- Текущие runtime-тесты уже проверяют реальную композицию с тестовыми HTTP/Socket.io серверами без NestJS, включая гонки и восстановление нескольких страниц. Гарантии, от которых пользователь явно отказывается, не сохраняются автоматически; остальные проверки пересматриваются после согласования нового поведения.

## Дерево решений

Согласовано в первом раунде:

1. Конкретная схема RootStore + Controllers + Domain Stores допускает уточнение.
2. Первым критерием читаемости станет отправка сообщения.

После исследования и ответов:

- Простой контракт отправки и восстановление последних 50 сообщений согласованы в раунде 3.
- Границы состояния, сценариев и транспорта; размещение в FSD.
- Время жизни корня приложения и авторизованного контекста; совместимость с ADR 0007.
- Владение историей активного диалога, пагинация и восстановление данных. Кэш нескольких историй исключён.
- Владение состоянием отправки, повторами и подтверждением через HTTP/WS.
- Ошибки, отмена и устаревшие результаты.
- Контракт чтения и изменения reactive state для UI.
- План будущей миграции и критерии приёмки.

Это направления интервью, а не принятые архитектурные решения.

## Раунд 1

**Q1.** Согласны считать RootStore + Controllers + Domain Stores целевой схемой, которую можно уточнять и упрощать, если конкретная часть не решает проблему читаемости?

Рекомендация: разделение состояния, сценариев и транспорта обязательно; точные классы, названия и число контроллеров обсуждаются. Ответ пользователя: «Да, схему можно уточнять».

**Q2.** Согласны взять отправку сообщения как первый контрольный сценарий: путь от кнопки Send через HTTP/WS до истории и превью прослеживается по явным вызовам, без поиска по компонентам и эффектам?

Рекомендация: начать с отправки; приоритет можно заменить сценарием, который вызывает основную боль. Ответ пользователя: «Да, начнём с отправки».

## Раунд 2

**Q3. Граница stores.** Распространять ли принцип «reactive model хранит и синхронно меняет состояние, controller выполняет асинхронный сценарий» на auth, историю, диалоги, composer и поиск?

Рекомендация: единое правило для всех этих моделей, без универсальных базовых классов и обязательного отдельного контроллера на каждое действие. Согласовано через Q9 в раунде 4.

**Q4. Жизненный цикл.** Сохранить ли ADR 0007: один корень приложения и новый вложенный авторизованный контекст на каждый успешный вход?

Рекомендация: сохранить; перепроверка сессии и reconnect не пересоздают контекст. Согласовано через Q9 в раунде 4.

**Q5. Истории диалогов.** Оставить ли историю только активного диалога?

Ответ пользователя: «Кэш не делаем, выглядит как усложнение». Решение: хранить историю только активного диалога, очищать её при переключении. Кэш нескольких историй исключён из целевой архитектуры; отдельная задача на него не планируется. Это согласованное отступление от исходного предложения хранить истории по `conversationId`. Дедупликация, пагинация и объединение HTTP/WS для активной истории сохраняются.

## Уточнение цели после раунда 2

Пользователь: «Давай упрощать и избавляться от attermptId. В целом нужно упрощать бизнес логику - текущая слишком сложная для тестового задания с чатом».

Принято: удалить `attemptId` из целевой модели отправки, включая запрос и сохранённое/публичное сообщение; отказаться от гарантии идемпотентного повтора через идентификатор попытки. Серверный `Message.id` сохраняется: это идентичность сохранённого сообщения и основа объединения его HTTP/WS-представлений. Отдельные POST-запросы могут создавать отдельные сообщения с одинаковым текстом; эвристика дедупликации по тексту не предполагается.

Базовое исходное задание — [INITIAL_REQUIREMENTS.md](../../INITIAL_REQUIREMENTS.md). `requirements.md` — журнал последующих договорённостей, а не исходный текст задания. Упрощения сравниваются с обоими источниками с явным указанием отказа от дополнительных гарантий.

## Раунд 3 — упрощённое поведение

**Q6. Отправка.** Достаточен ли обычный POST с текстом, блокировкой повторного нажатия во время запроса, очисткой формы после успеха и сохранением текста с ошибкой при неуспехе?

Рекомендация: да; без отдельной модели неопределённой попытки, специального Retry и автоматических повторов. Повторное нажатие после потери ответа — новый запрос, который может сохранить второе сообщение. Ответ пользователя на Q6–Q7: «на все да». Решение принято.

**Q7. Reconnect.** Достаточно ли при reconnect и возвращении на вкладку обновить последние 50 сообщений активного диалога и начать его пагинацию заново?

Рекомендация: да; не восстанавливать автоматически весь прежний загруженный диапазон. Старые сообщения доступны через Load more; обработка WS во время запроса и игнорирование устаревших ответов сохраняются. Это сокращает текущую гарантию восстановления всех пропущенных страниц, а не только переставляет код. Ответ пользователя на Q6–Q7: «на все да». Решение принято.

## Раунд 4 — оставшиеся границы

**Q8. Авторизация.** Достаточно ли проверки `/me` при запуске, login/register/logout и реакции на 401/`auth:ended`, с перепроверкой `/me` при ошибке подключения сокета, без клиентского таймера истечения и отдельной рассылки logout через localStorage?

Рекомендация: да. Проверка срока JWT и отключение истёкших сокетов остаются на backend. Вкладка узнаёт о завершении входа через socket или следующую проверку/запрос; мгновенное обновление всех отключённых вкладок не гарантируется. Сетевая ошибка не считается logout; при неуспешном серверном logout локальный вход не объявляется завершённым. Ответ пользователя на Q8–Q10: «на все да». Решение принято.

**Q9. Модули.** Достаточен ли один корень приложения, SessionController и ChatController в app, независимые rune-stores без HTTP и локальные состояния форм/поиска в UI?

Рекомендация: да. SessionController ведёт auth; ChatController — поиск пользователей, создание диалога, загрузку/пагинацию и отправку/приём сообщений. AuthStore остаётся в app, MessagesStore и ConversationsStore — в entities. UI получает readonly данные и необходимые actions через props; не получает весь RootStore. Текст, sending/error формы и результаты поиска не превращаются в глобальные stores. Асинхронные обращения к API выполняются контроллерами; UI может применять возвращённый результат поиска к своему локальному состоянию. Один новый авторизованный контекст на успешный вход согласно ADR 0007; старые запросы не меняют новый контекст. Это включает оставшиеся вопросы Q3–Q4. Ответ пользователя на Q8–Q10: «на все да». Решение принято.

**Q10. Список диалогов.** Сбрасывать ли его пагинацию при reconnect/возвращении на вкладку и загружать первую страницу, как для истории?

Рекомендация: да; infinite scroll подгружает остальные страницы по запросу пользователя. Обход прежнего загруженного диапазона списка не сохраняется. Ответ пользователя на Q8–Q10: «на все да». Решение принято.

## Принятые решения

- Конкретная структура RootStore + Controllers + Domain Stores допускает уточнение; обязательная цель — ясное разделение состояния, сценариев и транспорта.
- Первый контрольный сценарий — отправка сообщения: явный путь от действия UI через HTTP/WS до истории и превью.
- Кэш историй нескольких диалогов не вводится. Хранится история только активного диалога; переключение очищает её.
- Цель включает упрощение бизнес-логики для тестового задания. `attemptId` и гарантия идемпотентного повтора через него исключены; серверный идентификатор сообщения сохраняется.
- Отправка — POST с текстом, блокировка кнопки на время запроса, очистка после успеха, текст и ошибка при неуспехе. Нет отдельной модели неопределённой попытки, специального Retry и автоматического повтора.
- После reconnect/возвращения на вкладку история сбрасывается до последних 50 сообщений; более старые загружаются вручную через Load more. Обход всех пропущенных страниц исключён.
- Q9 также подтверждён ответом пользователя «на все да»: один корень приложения, два контроллера в app, независимые stores без HTTP, локальные состояния UI, сохранение ADR 0007. Все вопросы Q1–Q10 закрыты.
- Реализация отложена по прямому указанию пользователя.
