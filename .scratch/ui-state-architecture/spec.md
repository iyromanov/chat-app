# Простая архитектура состояния и бизнес-логики чата

Статус: ready-for-agent — решения Q1–Q10 и итоговое общее понимание подтверждены пользователем 2026-10-16. По отдельному запросу реализована [задача 01 — авторизация и жизненный цикл](issues/01-simple-session-lifecycle.md); задачи 02–04 остаются запланированными. [Журнал обсуждения](discussion.md).

## Цель и границы

Сделать состояние и бизнес-сценарии понятными для тестового задания: одна явная точка входа в сценарий, независимые реактивные хранилища, простой жизненный цикл. Сокращать бизнес-логику, а не только перемещать её между файлами.

Исходное задание — [INITIAL_REQUIREMENTS.md](../../INITIAL_REQUIREMENTS.md). Для затронутых сценариев эта спецификация заменяет дополнительные гарантии из [прежней спецификации](../chat-app/spec.md); незатронутое поведение сохраняется. Правила проекта — [CODING_STANDARDS.md](../../CODING_STANDARDS.md).

В объём будущей реализации входят frontend и удаление `attemptId` из контрактов и backend. Новые библиотеки, переписывание HTTP-клиента, переработка оформления и реализация stories не входят в эту миграцию.

## Согласованные упрощения

| Область             | Целевое поведение                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| Отправка            | Обычный POST с текстом, без `attemptId`                                                                       |
| Повтор              | Новое нажатие — новый запрос; идемпотентность не гарантируется                                                |
| Форма отправки      | Локальные текст, sending и ошибка; без отдельной неопределённой попытки и специального Retry                  |
| История             | Только активный диалог, без кэша нескольких историй                                                           |
| Обновление истории  | Последние 50 сообщений, сброс старой пагинации; более старые — Load more                                      |
| Обновление диалогов | Первая страница, сброс старой пагинации; остальные — infinite scroll                                          |
| Авторизация         | `/me`, login/register/logout, HTTP 401 и `auth:ended`; без клиентского таймера и localStorage-рассылки logout |

Обновление первых страниц применяется при reconnect и возвращении на вкладку. Автоматического восстановления всего пропуска и ранее загруженного диапазона нет. Данные остаются в MongoDB и доступны через обычную пагинацию.

## Ответственность модулей

| Модуль                                       | Ответственность                                                                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Корень приложения (`RootStore`)              | Создаёт зависимости, связывает callbacks, запускает и освобождает ресурсы                                                       |
| `SessionController` в app                    | `/me`, login/register/logout, потеря авторизации, координация авторизованного контекста                                         |
| `ChatController` в app                       | Поиск пользователей, создание/выбор диалога, загрузка и пагинация, отправка, события, согласованное обновление истории и превью |
| `AuthStore` в app                            | Явное реактивное состояние авторизации и синхронные переходы                                                                    |
| `MessagesStore` в entities/message           | История активного диалога, курсор, loading/error, синхронное объединение по Message ID                                          |
| `ConversationsStore` в entities/conversation | Список и превью, курсор, loading/error, синхронное обновление и сортировка                                                      |
| HTTP-клиент и SocketClient                   | Транспорт, типизация и ошибки; без знания stores                                                                                |
| Компоненты                                   | Отображение, события пользователя, локальные состояния форм и поиска, вызовы actions                                            |

Stores используют Svelte 5 runes в `.svelte.ts`. Они не выполняют HTTP, не владеют socket и не обращаются друг к другу. Контроллеры получают необходимые зависимости явно; не получают весь RootStore и не содержат реактивное состояние UI. Приватные технические поля для актуальности запросов допустимы.

Текст сообщения, sending/error формы, поисковый запрос и результаты поиска остаются локальными. Запрос поиска выполняет ChatController, возвращая данные вызывающему UI; устаревший результат поиска не заменяет более новый. Отдельные глобальные composer/search stores не нужны.

UI читает доменные данные через readonly TypeScript-контракт и изменяет их через actions. Отдельный runtime freeze не требуется. Зависимости передаются через props; нижние слои не импортируют app. DOM-эффекты для прокрутки и размера поля допустимы; синхронизация доменных данных через `$effect` исключена. Универсальные BaseStore/BaseController, event bus и отдельный класс на каждое действие не вводятся.

Ориентировочные места модулей, без обязательной перестройки всех каталогов:

```text
apps/web/src/
  app/
    runtime/       корень и авторизованный контекст
    auth/          AuthStore, SessionController
    chat/          ChatController
    realtime/      SocketClient
  entities/
    message/       MessagesStore
    conversation/  ConversationsStore
  shared/api/      существующий HTTP-клиент
  pages/, widgets/, features/  UI и передаваемые actions
```

## Жизненный цикл и авторизация

Один корень на экземпляр клиентского приложения. При каждом успешном входе, включая восстановление входа, создаётся новый авторизованный контекст с HTTP-клиентом, ChatController, stores и socket согласно [ADR 0007](../../docs/adr/0007-authenticated-client-context.md). Обычная перепроверка сессии и reconnect сохраняют контекст. На сервере общего пользовательского singleton нет.

Начальная проверка использует существующий `/api/auth/me`: 200 — authenticated, 401 — guest, сетевая ошибка/5xx — ошибка проверки с возможностью повторить. Login/register используют пользователя из существующего ответа, без обязательного дополнительного `/me`.

Успешный logout или подтверждённая потеря авторизации освобождает контекст, отключает socket и очищает пользовательские данные. Ошибка серверного logout сохраняет вход и показывается пользователю; 401 означает, что вход уже недействителен. Поздний ответ, включая 401 прежнего контекста, не завершает новый вход.

Проверка срока JWT и отключение истёкших соединений остаются на backend. Убираются клиентский таймер deadline и отдельная рассылка logout через localStorage. Отключённая вкладка узнаёт об окончании входа при следующем запросе/проверке/подключении; мгновенная синхронизация всех вкладок не гарантируется. При ошибке подключения socket SessionController перепроверяет `/me`; сетевой сбой не считается logout. См. [ADR 0009](../../docs/adr/0009-server-driven-client-auth.md).

Корень связывает существующие события `auth:ready`, `auth:ended`, `message:created`, `conversation:created`. Соединение создаётся после подтверждения авторизации. Повторное монтирование не создаёт второе соединение или обработчики. Dispose снимает подписки и делает старые операции неактуальными.

## Контрольный сценарий: отправка сообщения

1. Форма передаёт conversationId и текст в action отправки; блокирует повторное нажатие на время запроса.
2. ChatController отправляет POST через существующий HTTP-клиент. Запрос не содержит `attemptId`; backend валидирует текст, проверяет участие, сохраняет обычное сообщение и рассылает событие.
3. HTTP-ответ и `message:created` проходят через одну операцию применения сообщения в ChatController.
4. MessagesStore добавляет/обновляет сообщение по серверному ID, если открыт его диалог. ConversationsStore обновляет превью и порядок. Повторное представление того же Message ID не создаёт второй элемент.
5. После успешного POST форма очищает отправленный текст. При ошибке сохраняет его и показывает ошибку. Поздний результат не изменяет новую форму или другой диалог.

WS-событие не подтверждает отдельную клиентскую попытку: такой модели больше нет. Если сервер сохранил сообщение, а HTTP-ответ потерялся, сообщение может появиться через WS при ошибке запроса в форме. Повторное нажатие может создать второе сообщение. Дедупликации по тексту/времени и автоматической очереди офлайн-отправки нет. См. [ADR 0008](../../docs/adr/0008-simple-message-delivery.md).

## Загрузка, события и ошибки

- Выбор диалога очищает предыдущую историю и загружает последние 50 сообщений. Выбор остаётся локальным состоянием страницы согласно существующей навигации.
- Load more использует существующий cursor. Сохраняются сортировка сообщений `(createdAt, id)`, сортировка диалогов по активности и объединение по серверным ID.
- Reconnect/возвращение на вкладку обновляет историю и список с первых страниц, сбрасывая старые курсоры и диапазоны. Отдельного цикла обхода пропуска нет.
- События, полученные во время обновления, объединяются с ответом HTTP. Более свежие сообщения/превью не затираются устаревшим ответом. Старый загруженный диапазон при этом не удерживается как кэш.
- Событие другого диалога обновляет его превью, но не добавляет сообщения в открытую историю. Если данных неизвестного диалога недостаточно, ChatController синхронизирует список через существующий API; store не делает запрос самостоятельно.
- Поздние ответы после переключения диалога, выхода, dispose или нового входа не применяются. Используется локальная проверка актуальности/отмена, без универсального framework.
- Ошибки отображаются рядом с соответствующей формой/списком. Ошибка фонового обновления не завершает вход и не уничтожает отображаемые данные; повтор обновления доступен. Переподключением транспорта управляет существующий Socket.io.

## Проверка будущей реализации

Сохранить текущие проверки композиции с тестовыми HTTP/Socket.io серверами. Тесты идемпотентного повтора и полного восстановления диапазона заменить проверками нового поведения. Не заменять весь набор тестами только с mocks контроллеров; дополнительные unit-тесты нужны для самостоятельного поведения, не покрытого интеграционными проверками.

Критерии приёмки:

- Регистрация, login, `/me`, logout и ошибки работают; 401 завершает только актуальный вход, сетевой сбой не вызывает logout.
- Отправка сохраняет сообщение и доставляет его второму участнику; HTTP/WS одного Message ID не дублируют его в UI.
- Во время отправки кнопка заблокирована; успех очищает форму, ошибка сохраняет текст. `attemptId`, неопределённых попыток и специального Retry нет.
- История хранится только для активного диалога; переключение и старые ответы не смешивают данные.
- Reconnect/возвращение на вкладку обновляет первые страницы; курсоры сбрасываются, Load more/infinite scroll работают.
- WS во время загрузки не теряется; устаревший HTTP не откатывает превью. Неизвестные диалоги синхронизируются через controller.
- Один socket и один комплект обработчиков на контекст; dispose и logout освобождают их.
- Stores независимы и не содержат HTTP; UI не изменяет доменные данные напрямую; импорты соблюдают FSD.
- Права доступа, валидация текста, уникальность пары участников и серверная проверка JWT сохраняются.
- Для будущих изменений выполняются `pnpm generate`, `pnpm check`, `pnpm test`, `pnpm build`; backend-интеграционные тесты требуют Docker/Testcontainers.
