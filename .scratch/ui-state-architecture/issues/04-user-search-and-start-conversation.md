# 04: Поиск пользователей и начало переписки через actions

**What to build:** пользователь ищет собеседника, выбирает его, открывает существующий или новый диалог и отправляет сообщение. Компоненты управляют локальным UI, а асинхронный сценарий выполняет ChatController.

**Blocked by:** [03 — Загрузка переписки и простое обновление после reconnect](03-chat-loading-and-refresh.md): используется готовый сценарий выбора и загрузки диалога.

**Status:** ready-for-agent

**Spec:** [Простая архитектура состояния и бизнес-логики чата](../spec.md).

## Границы работы

Перенести HTTP-поиск и создание диалога из компонентов/reactive models в actions ChatController. Поисковый запрос, результаты, курсор и loading/error остаются локальными состояниями UI; controller возвращает данные и не создаёт новый глобальный store поиска.

Начало переписки обновляет список и использует единый сценарий выбора диалога, созданный в тикете 03. Удалить прежние дублирующие цепочки запросов/обновлений, сохранив существующий интерфейс и правила поиска. Проверить завершённую миграцию по [ADR 0010](../../../docs/adr/0010-client-state-and-controllers.md).

## Acceptance criteria

- [ ] Поиск username выполняется через ChatController по существующему API. Пустой запрос, отсутствие результатов, loading, ошибка и подгрузка пользователей работают по прежнему контракту.
- [ ] Поисковое UI хранит локально запрос, результаты и состояния операции. Устаревший ответ не заменяет результаты более нового запроса; результат прежнего входа не попадает в новый UI.
- [ ] Выбор пользователя создаёт или возвращает существующий диалог, обновляет список и открывает историю через общий action выбора. Компонент не координирует несколько доменных stores самостоятельно.
- [ ] Для пары участников сохраняется один диалог; повторное начало переписки открывает его. Новый пустой диалог отображается у обоих участников через существующий `conversation:created`.
- [ ] После открытия диалога можно отправить сообщение и получить ответ собеседника; работают сценарии предыдущих тикетов, включая обновление после reconnect.
- [ ] Компоненты поиска/начала переписки не выполняют HTTP напрямую. Отдельного глобального search/composer store и параллельной реализации прежних actions не остаётся.
- [ ] Все целевые доменные stores независимы и не содержат HTTP; асинхронные сценарии принадлежат двум контроллерам. Корень занимается композицией и жизненным циклом, UI получает только необходимые данные/actions; FSD соблюдается.
- [ ] Автоматические проверки наблюдаемого поведения покрывают поиск, старые ответы и создание/повторное открытие диалога. Текущие проверки композиции сохраняются; полноценный новый стек браузерных тестов не требуется.
- [ ] Выполнена общая проверка входа, поиска, создания диалога, отправки/приёма, пагинации, reconnect и выхода. Документация описывает согласованные упрощения; несвязанные backend/UI/stories изменения отсутствуют.
- [ ] `pnpm check`, `pnpm test` и `pnpm build` проходят; актуальность сгенерированных артефактов проверена штатной командой. Backend-интеграционные тесты выполняются с Docker/Testcontainers.
