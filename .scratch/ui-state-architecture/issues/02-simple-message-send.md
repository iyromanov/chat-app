# 02: Простая отправка и получение сообщений без attemptId

**What to build:** пользователь отправляет текст обычным запросом, видит сохранённое сообщение и получает сообщения собеседника в реальном времени. Форма показывает ход запроса и ошибку; отдельной неопределённой попытки и специального Retry нет.

**Blocked by:** [01 — Простая авторизация и жизненный цикл приложения](01-simple-session-lifecycle.md): используются корень и авторизованный контекст, подготовленные в этом тикете.

**Status:** ready-for-agent

**Spec:** [Простая архитектура состояния и бизнес-логики чата](../spec.md).

## Границы работы

Подключить обычный ChatController к авторизованному контексту. Отправка и обработка входящего сообщения используют единую операцию применения сохранённого сообщения, обновляющую историю открытого диалога и превью списка.

Удалить `attemptId` из запроса, публичного сообщения, контрактов, backend-модели новых сообщений и клиентской модели. Убрать проверку повторной попытки, конфликт изменённого текста и индекс идемпотентности. Предусмотреть удаление уже существующего индекса в MongoDB без потери переписки; одного удаления декларации индекса недостаточно. Обновить OpenAPI/HTTP-клиент штатным генератором.

Следовать [ADR 0008](../../../docs/adr/0008-simple-message-delivery.md) и [ADR 0010](../../../docs/adr/0010-client-state-and-controllers.md). Серверный Message ID сохраняется. Загрузка истории и списка пока может использовать прежнюю реализацию; окончательный перенос этих операций и обновления после reconnect относится к тикету 03. Параллельных хранилищ одних данных не создавать.

## Acceptance criteria

- [ ] POST содержит текст без `attemptId`; сервер проверяет текст и участие, сохраняет сообщение и отправляет существующее событие обоим участникам, включая отправителя.
- [ ] Новые сообщения сохраняются без `attemptId`; публичные HTTP/WS-ответы не содержат его. Существующая переписка читается после обновления.
- [ ] Удалена идемпотентность по попытке и соответствующий индекс, включая уже созданный индекс в существующей БД. Обычная повторная отправка одинакового текста может сохранить отдельные сообщения и не упирается в прежнее ограничение уникальности.
- [ ] OpenAPI и типизированный HTTP-клиент обновлены генератором; существующий клиент и транспорт переиспользуются.
- [ ] Форма вызывает action ChatController; текст, sending и ошибка локальны. Кнопка заблокирована во время запроса, успех очищает отправленный текст, ошибка сохраняет текст и показывается пользователю.
- [ ] Удалены отдельная неопределённая попытка, специальный Retry, подтверждение попытки по WS/истории и автоматические повторы. Потеря HTTP-ответа не скрывается эвристикой по тексту или времени.
- [ ] HTTP-ответ и `message:created` применяются через один обработчик. Повторное представление одного серверного Message ID не создаёт дубля истории; превью и порядок диалогов обновляются согласованно.
- [ ] Событие другого диалога не попадает в открытую историю. При недостатке данных о неизвестном диалоге синхронизация инициируется через ChatController и существующий API.
- [ ] Поздний результат отправки не очищает новую форму или другой диалог; завершённый контекст не меняет данные нового входа.
- [ ] Права доступа, валидация текста и серверная проверка JWT сохраняются. Тесты идемпотентного повтора заменены проверками обычной отправки и объединения HTTP/WS; сохранены проверки композиции через тестовые HTTP/Socket.io серверы.
- [ ] Документация описывает возможность второго сообщения при повторной отправке после потери ответа. `pnpm generate`, `pnpm check`, `pnpm test` и `pnpm build` проходят; backend-тесты выполняются с Docker/Testcontainers.
