# Real-time Chat Application

**Status:** ready-for-agent

## Problem Statement

Пользователям нужно находить друг друга, начинать личную переписку и получать сообщения без перезагрузки страницы. История должна сохраняться после выхода, перезагрузки и временного отсутствия связи; сообщения и диалоги должны быть доступны только участникам.

Результат тестового задания должен запускаться локально по README, демонстрировать читаемый код на заданном стеке и базовую обработку ошибок. Дополнительный согласованный сценарий — запись и просмотр коротких видеоисторий с ограниченным сроком жизни и персональным состоянием просмотра.

## Solution

Веб-приложение на NestJS, SvelteKit и TypeScript с MongoDB: регистрация и вход, поиск пользователей, личные диалоги, сохранённая история и доставка событий через Socket.io. Интерфейс на английском языке, с простым адаптивным оформлением Flowbite Svelte и Tailwind CSS, состояниями загрузки, ошибок и отсутствия данных.

Пользователь отправляет сообщение через REST API. После сохранения сервер доставляет событие всем подключённым вкладкам участников через Socket.io. После восстановления связи клиент получает актуальное состояние через REST. Повтор одной отправки не создаёт дубликат.

Видеоистории записываются с камеры, публикуются на 24 часа и доступны всем авторизованным пользователям. Лента выделяет непросмотренных авторов, перемещает полностью просмотренных в конец и сохраняет состояние просмотра между входами и устройствами.

Приоритет исполнения: полностью рабочее ядро чата, Docker Compose, тесты и README, затем видеоистории. Целевой бюджет — 12 часов с допустимым небольшим превышением.

## User Stories

### Регистрация и сессии

1. Как посетитель, я хочу зарегистрироваться с email, username и паролем, чтобы пользоваться приложением.
2. Как посетитель, я хочу получать понятные ошибки некорректных регистрационных данных, чтобы исправлять их.
3. Как посетитель, я хочу получать ошибку занятого email или username независимо от регистра букв, чтобы выбрать уникальные данные.
4. Как новый пользователь, я хочу сразу входить после регистрации, чтобы начать общение без повторного ввода пароля.
5. Как пользователь, я хочу входить по email и паролю, чтобы возвращаться к переписке.
6. Как пользователь, я хочу получать понятную ошибку неверных учётных данных, чтобы понимать причину неудачного входа.
7. Как пользователь, я хочу сохранять вход после перезагрузки и закрытия браузера в пределах срока сессии, чтобы не входить каждый раз.
8. Как пользователь, я хочу выходить из текущей сессии во всех её вкладках, чтобы прекратить доступ из этого браузера.
9. Как пользователь, я хочу сохранять независимую сессию в другом браузере при выходе из текущего, чтобы не терять доступ на другом устройстве.
10. Как пользователь, я хочу при истечении сессии переходить к входу, чтобы восстановить доступ.
11. Как пользователь, я хочу после выхода очистить авторизацию всех вкладок текущего браузера и отключить их соединения, а после истечения JWT потерять доступ к приватным действиям, чтобы завершать работу с приложением.
12. Как посетитель, я хочу попадать на вход при открытии приватного экрана, чтобы понимать, как получить доступ.

## Implementation Decisions

### Язык кода и приложения

- Все комментарии в коде, включая JSDoc/TSDoc, весь текст UI приложения и все сообщения об ошибках пишутся на английском. Это включает ошибки валидации, HTTP API, Socket.io и внутренние ошибки приложения.
- Требование распространяется на существующий и новый код. Пользовательский контент — сообщения, username и другие введённые данные — сохраняется на языке пользователя. Документация проекта может оставаться на русском.

### Стек и организация

- Backend — NestJS и TypeScript; frontend — SvelteKit и TypeScript; база данных — MongoDB; доставка событий — Socket.io.
- Web и API — два приложения одного pnpm workspace с единым lockfile и корневыми командами. Решение соответствует принятому ADR о workspace. Общие пакеты добавляются при конкретной необходимости.
- UI — Flowbite Svelte и Tailwind CSS. Готовые компоненты импортируются из npm-пакета flowbite-svelte с единообразным стандартным оформлением; отдельная дизайн-система не создаётся.
- Svelte stores управляют состоянием авторизации, сообщений и диалогов.
- Основные модули backend: авторизация, пользователи, диалоги, сообщения, gateway событий; отдельный модуль видеоисторий реализуется последним.
- Docker Compose запускает web, API и MongoDB; доступ пользователя к приложению, HTTP API и Socket.io осуществляется через один адрес localhost. Данные MongoDB и видео сохраняются в постоянных volumes. Для работы не нужны облачные сервисы.

### Frontend: FSD и клиентская загрузка

- Frontend следует FSD: app, pages, widgets, features, entities, shared; слои и срезы создаются по необходимости. Используются публичные интерфейсы срезов и автоматическая проверка допустимых импортов.
- Маршрутизация SvelteKit адаптируется к app. Переписка не рендерится на сервере: браузер сначала восстанавливает авторизацию через API, затем загружает данные и подключает Socket.io. Пока авторизация проверяется, показывается загрузка; без JWT — вход.
- App владеет авторизацией, жизненным циклом соединения и связыванием событий со stores. Pages собирают экраны; widgets содержат самостоятельные блоки списка диалогов, переписки и историй; features реализуют пользовательские действия; entities содержат предметные данные и stores; shared содержит UI и транспортные библиотеки без предметной логики.
- Авторизация не импортируется нижними слоями из app. Транспорт Socket.io не знает о предметных stores; app связывает событие с обновлением сообщений и диалогов, не создавая зависимость одного entity-среза от другого.
- Stores принадлежат экземпляру приложения, не общему серверному состоянию, и очищаются при выходе. Одно Socket.io-соединение создаётся на вкладку только в браузере.

### Backend: модули и валидация

- NestJS-модули организованы по предметным областям. Контроллеры и gateway вызывают прикладные сервисы; правила, права и инварианты реализуются в сервисах. Доступ к модели другого модуля выполняется через его экспортируемые сервисы.
- HTTP-авторизация выполняется guards с явно публичными операциями регистрации и входа. JWT проверяется также при Socket.io handshake; входящие обработчики событий, если они есть, защищаются отдельно.
- Для аутентификации максимально используются `@nestjs/passport` и готовые стратегии Passport: `passport-local` для входа по email и паролю, `passport-jwt` для проверки JWT из HttpOnly cookie; guards строятся на `AuthGuard` из `@nestjs/passport`. Выпуск JWT выполняется через `@nestjs/jwt`.
- Собственный код аутентификации ограничивается прикладной логикой и необходимой интеграцией: регистрацией и поиском пользователя, вызовом библиотеки хеширования и проверки пароля, настройкой cookie, подключением проверки к Socket.io и управлением сроком соединений. Механизмы аутентификации, предоставляемые библиотеками, не дублируются. Требование распространяется также на уже реализованную JWT-защиту; её приведение к этому подходу входит в задачу 02.
- Принадлежность диалога и срок доступности истории проверяются прикладными сервисами, независимо от транспортных проверок.
- Zod-схемы проверяют входные body, query и параметры маршрута через NestJS pipes. DTO создаются из схем через nestjs-zod; схемы хранения Mongoose отделены от транспортных контрактов.
- Универсальный репозиторий, CQRS и отдельный класс на каждое действие не вводятся без конкретной необходимости.

### Контракты, OpenAPI и HTTP-клиент

- Общий workspace-пакет содержит Zod-схемы запросов, публичных ответов и Socket.io-событий, а также выводимые типы; не зависит от NestJS, Mongoose или Svelte. Frontend использует схемы для валидации форм.
- В публичных данных идентификаторы — строки, даты — ISO-строки. Документы Mongoose, хеши и другие внутренние данные не возвращаются клиенту.
- Списки возвращают items и nextCursor; отсутствие курсора обозначает конец списка. Ошибка содержит стабильный code, понятный message и при необходимости ошибки полей. Внутренние ошибки БД и stack trace не передаются клиенту.
- NestJS формирует OpenAPI через @nestjs/swagger с интеграцией nestjs-zod. Контроллеры описывают маршруты, статусы и авторизацию; поля DTO выводятся из Zod. Swagger UI доступен для локальной проверки API.
- Из OpenAPI генерируются HTTP-типы через openapi-typescript; запросы выполняет openapi-fetch через сгенерированные методы по `operationId`. URL и HTTP-методы инкапсулированы в генерируемом клиенте; прикладной код не прописывает маршруты. Генерация HTTP не покрывает Socket.io и не заменяет runtime-валидацию.
- Фабрика клиента в shared принимает базовый URL и fetch, настраивает cookie и единое преобразование ошибок. Клиент создаётся для экземпляра приложения и используется entity- и feature-срезами. App связывает потерю авторизации с очисткой auth-store без обратного импорта из shared.
- Команды workspace экспортируют OpenAPI, генерируют типы и проверяют актуальность артефактов. Изменение HTTP API сопровождается обновлением документа и типов; сгенерированные типы не редактируются вручную.

### MongoDB: схемы, индексы и курсоры

- Используется Mongoose через @nestjs/mongoose. Коллекции: User, Conversation, Message, Story, StoryView. Коллекции Session и списка отозванных JWT нет.
- User хранит учётные данные и нормализованные email/username; Conversation — двух участников и уникальный ключ неупорядоченной пары; Message — диалог, отправителя, текст, время и идентификатор попытки; Story — автора, сведения о файле и срок; StoryView — зрителя, историю и время просмотра.
- Сообщения и истории — отдельные документы, а не неограниченно растущие массивы внутри диалога или пользователя.
- Уникальные индексы защищают нормализованные email и username, пару участников, сочетание диалога/отправителя/идентификатора попытки и пару зрителя/истории, в том числе при конкурентных запросах.
- Последнее сообщение и время активности диалога вычисляются из Message при чтении списка через индексированную агрегацию. Их копия в Conversation не хранится; отправка не требует обновления второго документа и многодокументной транзакции. Более сложное чтение принято для масштаба тестового.
- Индексы поддерживают сообщения внутри диалога, выборку диалогов участника и активные истории автора.
- Пагинация по значениям сортировки, без offset: пользователи — нормализованный username и ID; сообщения — время создания и ID; диалоги — вычисленная активность и ID. Для сообщений поддерживаются загрузка старой истории и получение пропущенных новых сообщений.
- Курсоры валидируются и привязаны к параметрам запроса. Полный снимок изменяемого списка на всё время прокрутки не создаётся; события и синхронизация обновляют порядок диалогов, клиент устраняет дубликаты.

### Авторизация и данные пользователей

- Регистрация принимает email, username и пароль. Email обязателен и проверяется на формат; email и username уникальны без учёта регистра. Отображаемый username сохраняет выбранное написание.
- Username содержит 3–30 символов: латинские буквы, цифры и подчёркивание. Пароль содержит 8–128 символов, без обязательного состава; хранится в виде стойкого хеша.
- После регистрации выдаётся JWT. Вход выполняется по email и паролю.
- JWT хранится в HttpOnly cookie, сохраняющей вход после закрытия браузера, и действует 24 часа без автоматического продления.
- Авторизация stateless: сервер проверяет подпись и срок JWT без коллекции Session и без запроса к хранилищу сессий на каждый защищённый HTTP-запрос. Бизнес-операции при необходимости обращаются к MongoDB.
- Выход удаляет cookie, очищает клиентскую авторизацию всех вкладок текущего браузера и отключает относящиеся к текущему входу Socket.io-соединения. Независимый вход другого браузера сохраняется.
- Выход не отзывает JWT на сервере: ранее скопированный токен остаётся пригодным для HTTP и нового Socket.io-подключения до истечения срока. Это согласованное ограничение.
- Приватные маршруты, API и Socket.io проверяют авторизацию. Истечение JWT запрещает приватные HTTP-запросы, отключает соответствующие Socket.io-соединения; клиент показывает вход. Проверки только при первоначальном подключении недостаточно для соблюдения срока действия.
- Пароли и их хеши не возвращаются клиенту; email других пользователей не раскрывается в поиске и списках.

### Пользователи и диалоги

- Поиск username — по подстроке без учёта регистра, на сервере и по всему набору пользователей. Пустой запрос возвращает остальных пользователей; текущий пользователь исключён.
- Список пользователей сортируется по username. Списки пользователей и диалогов загружаются порциями по 50 через infinite scroll.
- Диалог содержит ровно двух разных пользователей. Для неупорядоченной пары участников существует ровно один диалог; уникальность обеспечивается также при конкурентном создании.
- Начало переписки сразу создаёт или возвращает диалог. Новый пустой диалог появляется у обоих участников с подписью “No messages”.
- Список диалогов доступен только их участнику. Он показывает username собеседника, последнее сообщение и время; сортируется по последнему сообщению, а для пустого диалога — по времени создания, от новых к старым.
- Создание диалога и новое сообщение обновляют списки всех подключённых вкладок участников. Подгрузка страниц и события объединяются без дубликатов.
- Все операции чтения истории, отправки сообщения и доставки событий проверяют участие в диалоге. Знание идентификатора чужого диалога не даёт доступа.

### Сообщения и события

- Создание диалогов, отправка сообщений и чтение данных выполняются через REST API. Gateway используется для доставки событий новых диалогов и сохранённых сообщений.
- Текст сообщения содержит 1–2000 символов после удаления пробелов по краям. Пустой результат запрещён; внутренние переносы строк сохраняются. Сервер проверяет входные данные.
- Отправка содержит идентификатор попытки, который сохраняется при повторном запросе. Одна и та же отправка создаёт не более одного сообщения, включая конкурентные повторные запросы.
- Повтор с тем же идентификатором, отправителем, диалогом и тем же нормализованным текстом возвращает существующее сообщение. Другой текст для той же попытки возвращает конфликт.
- Сообщение сначала сохраняется в MongoDB, затем сервер рассылает событие всем подключённым вкладкам обоих участников, включая отправителя. Ответ REST и событие относятся к одному сохранённому сообщению.
- Клиент объединяет сообщения по серверному идентификатору, чтобы ответ HTTP, события и восстановление истории не создавали дубликатов.
- При открытии диалога загружаются последние 50 сообщений; отображение — от старых к новым. Более старые сообщения загружаются отдельными порциями кнопкой «Load more».
- Порядок и постраничная загрузка должны быть однозначными также для сообщений с одинаковым временем; конкурентная отправка не должна приводить к пропускам и повторному отображению.
- После перезагрузки, повторного входа и офлайна история читается из MongoDB. После переподключения клиент сверяет историю и список диалогов через REST, включая сообщения, пропущенные во время восстановления соединения.
- Первоначальная загрузка и восстановление объединяют события, пришедшие во время REST-запросов, с загруженными данными. Пропущенные сообщения загружаются всеми необходимыми порциями; дополнительно чат синхронизируется при возвращении на вкладку.
- MongoDB — источник истины, Socket.io — оперативные уведомления. Долговечная очередь событий и transactional outbox не вводятся: сбой между сохранением и рассылкой может задержать отображение сообщения до следующей синхронизации, но сохранённые данные остаются доступны.
- Интерфейс показывает состояние соединения. Успех отправки отображается только при подтверждении сохранения ответом API, событием или сверкой истории. При неопределённом результате доступна повторная попытка с прежним идентификатором.
- Автоматическая очередь новых сообщений для отправки во время офлайна не реализуется.

### Видеоистории: запись и публикация

- Запись выполняется через MediaRecorder API с камеры, со звуком при доступном микрофоне. При недоступном микрофоне допускается видео без звука с предупреждением; недоступная камера и неподдерживаемая запись показывают понятную ошибку.
- Таймер показывает время записи; запись автоматически останавливается через 15 секунд. До публикации доступны предварительный просмотр и пересъёмка.
- Публикация видео выполняется через авторизованный API с multipart/form-data, с проверкой входящих данных и лимита 25 МБ. Используется формат записи, поддерживаемый проверяемым браузером; конвертация и оптимизация видео не выполняются.
- Видео хранится на диске API в постоянном Docker volume; MongoDB содержит автора, сведения о видео, время публикации и истечения срока. У пользователя может быть несколько активных историй.
- Видео выдаётся через приватный API с проверкой сессии и срока действия истории, а не через общедоступный каталог файлов.
- Публикация сначала сохраняет файл, затем метаданные в MongoDB. Ошибка записи метаданных приводит к удалению файла; после аварии фоновая очистка убирает оставшиеся файлы без метаданных. Незавершённые загрузки не показываются в ленте; очистка не должна удалять активную загрузку.

### Видеоистории: лента и просмотр

- Лента содержит авторов с активными историями и доступна всем авторизованным пользователям. Выбор автора открывает его активные истории от старых к новым.
- Воспроизведение запускается нажатием пользователя. Навигация — кнопками «Previous» и «Next»; автоматическое переключение не требуется.
- Лента обновляется при открытии, возвращении на вкладку браузера и после собственной публикации. Отдельной кнопки обновления, периодического опроса и событий новых stories через Socket.io нет.
- Если пользователь остаётся на вкладке, новая чужая история появляется при следующем открытии ленты или возвращении на вкладку.
- Просмотр истории — персональная отметка пары «зритель — история», хранимая в MongoDB и сохраняемая между входами и устройствами. Повторная отметка той же истории не меняет смысл состояния.
- Просмотр засчитывается после фактического начала воспроизведения. Простое открытие просмотрщика и ошибка загрузки не считаются просмотром; досматривать до конца не нужно.
- Автор с хотя бы одной непросмотренной активной историей выделяется обводкой и находится перед полностью просмотренными авторами. У полностью просмотренного автора обводка меняется.
- Внутри обеих групп авторы сортируются по последней активной публикации, от новых к старым. Новая непросмотренная история возвращает автора в группу непросмотренных при следующем обновлении данных.
- Перестановка авторов после просмотра выполняется после закрытия просмотрщика, чтобы не менять порядок во время навигации. Просмотренные истории доступны повторно до истечения срока.
- Персональный учёт просмотра не добавляет счётчики просмотров, список зрителей или индикаторы прочтения сообщений.

### Видеоистории: истечение срока

- Срок жизни — 24 часа с момента публикации. Истёкшая история исключается из API ленты и не открывается через API видео независимо от фоновой очистки.
- Открытая лента убирает истёкшие истории. Если история воспроизводится в момент истечения, клиент прекращает просмотр и показывает «This story has expired».
- При работающем сервере фоновая очистка удаляет видео и запись истории в течение следующих 5 минут. При запуске после простоя сервер очищает просроченные истории.
- Очистка сначала удаляет файл, затем метаданные и отметки просмотра. При ошибке удаления файла информация для повторной попытки сохраняется. Повторная очистка уже удалённого файла не препятствует завершению удаления метаданных.
- Состояние просмотра рассчитывается по активным историям: истёкшие истории не удерживают автора в ленте и не делают его непросмотренным.

## Testing Decisions

### Согласованные границы

Автоматические тесты наблюдают внешнее поведение через HTTP API и авторизованные соединения Socket.io. Обе границы согласованы пользователем на стадии уточнения требований; дополнительных публичных границ для тестирования не требуется.

MongoDB запускается через Testcontainers. Тестам необходим работающий совместимый контейнерный runtime; требования и команда запуска описываются в README. Моки MongoDB не заменяют проверку уникальности, сохранения истории и конкурентных операций.

Backend-тесты выполняются Jest. Заменяемый источник времени позволяет проверять истечение JWT и stories, очистку и запуск после простоя без ожидания суток; тесты наблюдают результаты через согласованные HTTP/Socket.io-интерфейсы.

HTTP и Socket.io тесты проверяют backend, включая работу с БД, но не подтверждают исправность интерфейса или записи с камеры. UI и камера проверяются вручную в Chrome. Существующих тестов и образцов тестовой инфраструктуры в репозитории нет: проект начинается с документов требований.

### Принципы и обязательное покрытие

- Хороший тест описывает наблюдаемое поведение из этой спецификации, а не структуру контроллеров, репозиториев или приватных методов. Ожидаемые результаты выводятся из требований и заранее известных примеров.
- Авторизация: успешная регистрация и вход, некорректные данные, уникальность email и username без учёта регистра, недоступность приватного HTTP API и Socket.io без действующей сессии.
- Выход: HTTP-ответ очищает cookie, соответствующие Socket.io-соединения отключаются, независимый вход другого браузера сохраняется; очистка состояния всех вкладок дополнительно проверяется вручную. Скопированный JWT после выхода остаётся действительным до истечения срока — тесты не должны требовать серверного отзыва.
- Истечение JWT: прежний токен больше не даёт доступ к HTTP API и Socket.io; существующее соединение также отключается.
- Пользователи: поиск по подстроке без учёта регистра, исключение себя, отсутствие чужих email, получение следующих порций.
- Диалоги: создание пустого диалога, повторное и конкурентное создание одной пары без дубликатов, список только собственных диалогов.
- Сообщения: валидация текста, сохранение переносов, история и её подгрузка, сохранение после нового входа, повторная и конкурентная отправка одной попытки без дубликатов.
- Контракты: повтор попытки с другим текстом возвращает конфликт; публичные ответы и события соответствуют согласованным схемам. Пагинация проверяется также при одинаковом времени сообщений и с некорректными курсорами.
- Приватность: третий пользователь не читает историю, не отправляет сообщения в чужой диалог и не получает события участников. Попытка доступа проверяется через публичные границы.
- Доставка: REST-отправка приводит к событию Socket.io с сохранённым сообщением во всех подключённых вкладках участников; новое создание диалога также доставляется обоим участникам.
- Восстановление: сообщения, отправленные при отсутствии соединения получателя, доступны через REST после переподключения. Отдельно вручную проверяется объединение данных в UI без дубликатов.
- Истории: публикация, ограничения загрузки, доступ только с действующей сессией, несколько историй одного автора и доступ к видео до истечения срока.
- Персональный просмотр: повторная отметка не дублирует состояние, отметки одного зрителя не влияют на другого, повторный вход сохраняет отметки, полностью просмотренный автор меняет группу, новая история возвращает его к непросмотренным.
- Истечение: после 24 часов история недоступна через ленту и видео API независимо от очистки; удаление и очистка после простоя проверяются без реального ожидания суток, с управляемым временем. Проверки поведения остаются на согласованных публичных границах.
- Сбои публикации и очистки: неуспешная публикация не появляется в ленте; обработка повторных попыток очистки сохраняет ожидаемую доступность историй. API-проверки подтверждают доступность, но не доказывают физическое удаление файла или метаданных: это отдельно проверяется при ручной приёмке.
- ESLint, Prettier, TypeScript/Svelte и проверка актуальности OpenAPI/HTTP-типов дополняют сценарные тесты. ESLint контролирует направления импортов FSD и доступ через публичные интерфейсы срезов. Полный набор проверок запускается перед завершением реализации.
- Обязательная конфигурация проверяется при запуске; отсутствие нужных параметров даёт понятную ошибку.

### Ручная приёмка

- Два пользователя в независимых браузерных сессиях регистрируются, находят друг друга, создают один диалог и обмениваются сообщениями без перезагрузки.
- Дополнительные вкладки участников получают новые диалоги и сообщения; отключение и восстановление сети не приводит к потере сохранённой истории или дубликатам.
- Поиск, infinite scroll списков, загрузка старой истории, пустые состояния, загрузка и ошибки проверяются в интерфейсе.
- Запись, таймер, предварительный просмотр, пересъёмка, публикация и просмотр stories проверяются в актуальном Chrome на компьютере, включая отказ в доступе к камере и отсутствие микрофона.
- В Chrome проверяются отметка после начала воспроизведения, порядок авторов после закрытия просмотра, повторный просмотр и обновление ленты при возвращении на вкладку.
- Интерфейс проверяется на узкой ширине экрана. Полная совместимость записи с Safari, Firefox и мобильными браузерами не является критерием приёмки.
- Проверяющий следует README, запускает Compose, открывает один адрес localhost и убеждается, что данные сохраняются при обычном перезапуске контейнеров.
- Физическое удаление истёкших видео, метаданных и отметок, а также очистка файлов без метаданных проверяются отдельно осмотром тестового хранилища и MongoDB. Отказ API в доступе к истёкшей истории сам по себе не считается доказательством физической очистки.

## Out of Scope

- Групповые диалоги и диалог с собой.
- Файлы и изображения в сообщениях; редактирование и удаление сообщений.
- Индикаторы набора, присутствия онлайн, прочтения сообщений и счётчики непрочитанных.
- Восстановление пароля, подтверждение email и смена username.
- Серверные сессии, список отозванных JWT, немедленный отзыв скопированного токена при выходе, автоматическое продление JWT и очередь отправки новых сообщений во время офлайна.
- Загрузка готовых видео через пользовательский интерфейс, ручное удаление stories, реакции, счётчики просмотров и списки зрителей для автора.
- Фильтры, эффекты, конвертация, оптимизация размера видео и иной медиапроцессинг на backend.
- Автоматическое переключение между stories; мгновенная доставка новых stories через Socket.io, периодический опрос ленты и отдельная кнопка её обновления.
- MinIO, облачное хранилище и другие облачные зависимости приложения.
- Долговечная очередь событий, transactional outbox, многодокументные транзакции для отправки сообщения и полный снимок списка на время прокрутки.
- Push-уведомления, production-развёртывание, сложный дизайн и отдельная дизайн-система.
- Полный набор браузерных автотестов и гарантированная совместимость записи со всеми браузерами и мобильными устройствами.

- Исходное задание и журнал уточнений сохраняются отдельно. Эта спецификация объединяет окончательные согласованные требования без необходимости восстанавливать решения по хронологии чата.

- Следующая стадия — декомпозиция на самостоятельные проверяемые задачи с явными зависимостями, сохраняя приоритет рабочего чата перед видеоисториями.
