# Техническое уточнение

Статус: технические решения и общее понимание подтверждены пользователем.

Функциональный объём из [spec.md](spec.md) сохраняется с согласованным изменением выхода на stateless JWT. Спецификация дополнена архитектурой frontend, организацией backend, доступом к MongoDB и техническими контрактами. Проект из девяти задач принят пользователем; критерии дополнены согласованной технической частью.

## Раунд 1 — согласовано (Q29–Q33)

- Frontend: FSD с правилами импортов и публичными интерфейсами срезов; слои добавляются по необходимости. Маршрутизация SvelteKit адаптируется к слою app.
- Приватная область чата: клиентская загрузка данных через NestJS REST API; Socket.io запускается только в браузере. Пользовательские stores изолированы от общего серверного состояния.
- Backend: NestJS-модули по предметным областям; HTTP-контроллеры и gateway обращаются к прикладной логике, проверяющей права и инварианты. Доступ к MongoDB остаётся внутри владеющих данными модулей.
- MongoDB: Mongoose через интеграцию NestJS; модель данных и требования к индексам согласованы в следующих раундах.
- Инструменты: ESLint, Prettier, проверки TypeScript и Svelte; Jest для backend HTTP/Socket.io тестов с MongoDB в Testcontainers.
- FSD: направление зависимостей app → pages → widgets → features → entities → shared, публичные интерфейсы срезов, слои по необходимости; готовые UI-компоненты импортируются из flowbite-svelte, предметные композиции размещаются по слоям FSD.
- Приватная область не рендерит переписку на сервере. Клиент сначала проверяет сессию через API, затем загружает данные и подключает Socket.io; при проверке показывает загрузку, без сессии — вход.
- Контроллеры и gateway вызывают прикладные сервисы; другие модули получают доступ к данным через экспортируемые сервисы владельца, а не напрямую к его моделям.
- Универсальный репозиторий, CQRS и отдельные классы на каждое действие не вводятся без конкретной необходимости.
- Правила импортов FSD проверяются автоматически через ESLint согласно Q43; конкретная конфигурация выбирается при реализации.

## Раунд 2 — согласовано (Q34–Q35)

- Guards для аутентификации HTTP, проверка JWT при Socket.io handshake и защита входящих обработчиков при их наличии. Проверки участия в диалоге и срока истории выполняются в прикладных сервисах; выход отключает соединения текущего входа, истечение JWT также отключает действующие соединения.
- Zod-схемы транспортных контрактов, NestJS pipes для body/query/params; общий workspace-пакет контрактов для web и API. Mongoose-схемы остаются внутренними схемами хранения backend.

## Уточнение аутентификации — согласовано

- Для минимизации собственного кода используются `@nestjs/passport`, `passport-local` для входа по email и паролю, `passport-jwt` для проверки JWT из HttpOnly cookie и guards на основе `AuthGuard`. Выпуск JWT выполняется через `@nestjs/jwt`.
- Собственный код ограничен прикладной логикой и необходимой интеграцией: регистрацией и поиском пользователя, вызовом библиотеки хеширования и проверки пароля, настройкой cookie, подключением проверки к Socket.io и управлением сроком соединений. Библиотечные механизмы аутентификации не дублируются; проверки участия в диалоге остаются в прикладных сервисах.
- Уже реализованная JWT-защита приводится к этому подходу в задаче 02. Сохраняются stateless JWT, срок 24 часа, отсутствие серверного отзыва и проверка истечения с управляемым временем; решение ADR 0003 не меняется.

## Модель хранения — согласовано (Q36b)

- Коллекции User, Conversation, Message, Story и StoryView с отдельными документами сообщений и историй, ссылками на участников и индексами уникальности и выборки.
- User: учётные данные, username и нормализованные значения. Conversation: два участника и уникальный ключ пары. Message: диалог, отправитель, текст, время и идентификатор попытки. Story: автор, сведения о файле, публикация и истечение. StoryView: зритель, история и время просмотра.
- Уникальные индексы: нормализованные email и username; неупорядоченная пара участников; сочетание диалога, отправителя и идентификатора попытки; пара зрителя и истории.
- В API передаются строковые идентификаторы и даты в ISO-формате, не документы Mongoose.

## Транспортные контракты — согласовано (Q37)

- Общий workspace-пакет содержит Zod-контракты запросов, публичных ответов и событий.
- Списки возвращают items и nextCursor; отсутствие курсора означает конец списка.
- Ошибка содержит стабильный code, понятный message и при необходимости ошибки полей; внутренние ошибки БД и stack trace не передаются клиенту.
- REST-ответ отправки и Socket.io-событие содержат одинаковое публичное представление сохранённого сообщения.
- Повтор отправки с прежним идентификатором и тем же текстом возвращает существующее сообщение. Прежний идентификатор с другим текстом возвращает конфликт.

## Уточнение Q36a — согласовано

- Выбран stateless JWT без коллекции Session и без denylist. Guard проверяет подпись и срок JWT без чтения серверной сессии.
- JWT живёт 24 часа, хранится в HttpOnly cookie, автоматически не продлевается.
- Выход удаляет cookie, очищает состояние вкладок и отключает сокеты текущего входа; независимый вход другого браузера сохраняется.
- Копия ранее выданного JWT после выхода остаётся действительной до истечения, в том числе для нового Socket.io-подключения. Первоначальное требование немедленного серверного отзыва отменено; спецификация и проверки обновлены.
- Истечение JWT прекращает HTTP-доступ и действующие Socket.io-соединения.

## Согласованность и frontend — согласовано (Q38–Q40)

- Последнее сообщение и время активности диалога вычисляются при чтении списка из Message через агрегацию с индексами. В Conversation не хранится копия последнего сообщения; отправка не требует изменения двух документов или транзакции.
- Компромисс: запрос списка сложнее; это принято для масштаба тестового.
- FSD app: авторизация, восстановление входа, жизненный цикл Socket.io, связывание событий со stores. pages: сборка экранов. widgets: самостоятельные блоки списка диалогов, переписки и stories. features: пользовательские действия. entities: данные и stores пользователей, диалогов, сообщений и историй. shared: HTTP-клиент, транспорт Socket.io, UI и общие библиотеки.
- Нижние слои не импортируют auth-store из app. Транспорт не знает о предметных stores; связывание выполняется сверху. Entity-срезы не зависят друг от друга для совместного обновления по событию.
- Stores принадлежат экземпляру приложения и очищаются при выходе; Socket.io-подключение одно на вкладку.
- MongoDB — источник истины, Socket.io — оперативные уведомления после сохранения.
- При первоначальной загрузке и восстановлении события объединяются с REST-данными по идентификаторам; пропущенные сообщения загружаются всеми необходимыми порциями.
- Дополнительная синхронизация чата выполняется при возвращении на вкладку.
- Долговечная очередь событий и transactional outbox исключены. Сбой между сохранением и рассылкой может задержать доставку до следующей синхронизации; данные остаются в MongoDB.

## Пагинация, файлы и проверки — согласовано (Q41–Q43)

- Пагинация по курсорам значений сортировки, без offset: пользователи — нормализованный username и ID; сообщения — время создания и ID, с направлениями загрузки старых и пропущенных новых сообщений; диалоги — вычисленная активность и ID.
- Курсоры валидируются и привязываются к параметрам запроса. Порядок диалогов меняется через события и синхронизацию без дубликатов; полный снимок списка на всё время прокрутки не создаётся.
- Индексы поддерживают сообщения диалога, диалоги участника и активные истории автора.
- Публикация сохраняет файл, затем запись истории; ошибка записи в MongoDB приводит к удалению файла. Фоновая очистка убирает файлы без метаданных после аварии; незавершённые загрузки не отображаются в ленте.
- Очистка истёкшей истории удаляет файл, затем метаданные и отметки просмотра. При ошибке удаления файла сохраняется информация для повтора; срок проверяется независимо от очистки.
- Время backend передаётся через заменяемый источник для проверки истечения JWT/stories и очистки без реального ожидания суток. Результаты проверяются через HTTP/Socket.io.
- ESLint проверяет направления импортов FSD и обращения к внутренностям других срезов. Пакет контрактов не импортирует NestJS, Mongoose или Svelte.
- Обязательная конфигурация валидируется при запуске; README описывает проверки и необходимость Docker для Testcontainers.

## API-клиент — согласовано (Q44)

- Цепочка: Zod-схемы → NestJS DTO через nestjs-zod → OpenAPI через @nestjs/swagger → типы openapi-typescript → клиент openapi-fetch.
- Swagger UI документирует HTTP API. Контроллеры задают маршруты, статусы и авторизацию; поля DTO выводятся из Zod.
- Фабрика клиента в shared/api принимает базовый URL и fetch, настраивает cookie и единое преобразование ошибок. Клиент создаётся для экземпляра приложения; entity- и feature-срезы используют его для своих операций.
- App связывает потерю авторизации с auth-store, shared не импортирует app.
- Общий пакет Zod-контрактов сохраняется для валидации backend, форм и Socket.io-событий. Генерация HTTP-клиента не покрывает Socket.io.
- Генерируются HTTP-типы; запросы выполняет openapi-fetch. TypeScript-типы сами по себе не валидируют ответы во время выполнения.
- Добавляются команды генерации и проверки актуальности артефактов. Изменение API сопровождается обновлением OpenAPI и типов клиента; сгенерированные типы вручную не редактируются.

## Язык кода и приложения — согласовано

- Английский обязателен для всех комментариев в коде (включая JSDoc/TSDoc), всего текста UI и всех сообщений об ошибках: валидации, HTTP API, Socket.io и внутренних ошибок приложения. Требование охватывает существующий и новый код.
- Пользовательский контент сохраняется на языке пользователя; документация проекта может оставаться на русском. Первоначальное требование русского UI заменено английским; спецификация, стандарты и критерии приёмки обновлены.

## Итог

- Открытых технических выборов на стадии требований нет. Конкретная конфигурация инструментов и имена операций остаются реализационными деталями в пределах принятых решений.
- Технические решения перенесены в спецификацию; правила ревью — в документ стандартов, существенные компромиссы — в ADR.
- Итог подтверждён. Задачи публикуются отдельными Markdown-файлами в локальном трекере согласно принятой декомпозиции.
